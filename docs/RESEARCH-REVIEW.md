# Аудит исследователей, ветвления и журнала · v0.4.2

> Исторический отчёт о конкретной версии или запуске. Действующая инструкция — [PROJECT_GUIDE.md](PROJECT_GUIDE.md); карта прежних материалов — [HISTORY.md](HISTORY.md). Числа и настройки ниже относятся к проверенной здесь версии.

Это аудит версии v0.4.2. Поиск по времени, локальные серии и поведение при исчерпании обращений
обновлены в v0.5.0 и описаны в [TIME-SEARCH.md](TIME-SEARCH.md).

Дата: 22 октября 2026 года. Проверена актуальная `main` на момент начала работы:
`c7fb573568a87bc6be5757121b3f8a5d7aa3a394` (v0.4.1). Сохранены читаемая плоская поставка,
байтовая идентичность экспортируемых Python-модулей и исправление ошибок кредитов провайдера.

Основание для проверки — код и переданный консольный лог регрессионного запуска. Самих данных,
`state.sqlite` и сохранённых контекстов этого запуска в проверяемом репозитории нет. Поэтому новые
изменения не выдаются за измеренный прирост на скрытом тесте или за воспроизведение RMSE 43.9732.

## Что мешало исследователям

Основная проблема была в передаваемом им состоянии. Роли существуют, но полезные результаты
удалялись раньше избыточного профиля данных. Каталожный factory-код не содержит параметров
конкретного эксперимента: один `base_experiment_id` не сообщает модели ни настройки, ни оценку.
В переданном логе `retained_experiments=0` встречается во всех 15 сборках контекста. Это объясняет,
почему многие гипотезы снова сравнивают всё с Dummy, хотя лучшие решения уже обучены.

Вторая проблема — выполнение пачками: при одном обучающем процессе готовое предложение ждало
ответа второго исследователя. Это расходовало общее время без полезного обучения.

## Найденные ошибки и внесённые исправления

| Область | Было | Теперь | Проверка |
|---|---|---|---|
| Память результатов | Сначала удалялись все facts, затем профиль | Сначала сокращается избыточный профиль; измеренная база, donors и ближайшие факты защищены | Большой искусственный профиль сохраняет базовые параметры, score и неудачную попытку |
| Задание исследователю | Exploit/explore влияло на меню рецептов, но текст задания был одинаковым; промпт ссылался на отсутствующее `recent_experiments` | Явные `research_strategy`, `base_result`, инструкции по полям `facts`; роли чередуются | Проверены разные задания двух peers и смена ролей |

| Ошибки предложений | Ошибка сохранялась в журнале, но не попадала в следующий контекст | Краткий отказ передаётся отдельным failure fact без выдуманной метрики | Проверены отказы до создания experiment и ошибки реального жизненного цикла experiment |

| Плато | Время до создания/возобновления ветки считалось её застоем; неподходящие pre-idea bases участвовали в сравнении | Время считается после последнего запуска ветки/улучшения; сравниваются только допустимые для неё references | Проверены позднее создание, пауза/возврат и реальное улучшение внутри required-feature ветки |
| Применение принятой идеи | На простое применение известной фичи мог расходоваться новый запрос к LLM | Для совместимой собственной базы выполняется доверенный controlled transfer; известное обучение берётся из exact cache | Оба peers принимают фичу без LLM и без увеличения числа обучений при наличии результатов |
| Просроченные задания | Планировщик мог видеть всех peers занятыми и не дойти до кода истечения TTL | Expired issued/preparing orders закрываются до выбора исполнителя и отражаются в typed journal | Проверены освобождение двух peers и события `expired` |

## Как теперь организована работа

1. Dispatcher выбирает свободного равноправного peer и выдаёт ticket с branch/head revisions.
2. Свежая капсула содержит TaskContract, собственный код, эффективные параметры и оценку базы,
   ограничения ветки, краткую историю и явных donors. Текст чужой гипотезы остаётся данными.
3. Exploit настраивает собственную модель. Explore получает конкретное менее проверенное семейство.
   Один peer не заменяется постоянным лидером; стратегии меняются между раундами.
4. Пока один исследователь отвечает, уже готовая работа другого может обучаться в отдельном процессе.
   SQLite, выдача tickets, проверка lineage и применение результата остаются в основном потоке.
5. Новая переносимая идея всё ещё требует контролируемой пары и проверки на собственной базе другого
   peer. Улучшение со смешанными изменениями не выдаётся за доказательство эффекта конкретной фичи.
6. При fork сохраняются обе альтернативы. В `accept` известная идея сначала применяется к совместимой
   собственной базе; exact cache позволяет не повторять уже проведённое обучение. При несовместимом
   стартовом рецепте исследователь выбирает новый допустимый рецепт обычным путём.
7. База вне новых ограничений не участвует как допустимый incumbent или seed для плато. Она остаётся
   восстановленной исторической точкой. Global best по всем валидным решениям хранится отдельно.
8. Размер пачки, число API-заданий и переход к альтернативе учитывают оставшийся бюджет.
   В конце сравниваются все сопоставимые full evaluations; опубликованный CSV защищён прежним C18–C21.

## JSON и совместимость

`C00–C24`, `G00–G14`, `I00–I03`, `ExperimentPlan`, work order и формат графового экспорта сохранены.
В `GContextUser` добавлены два **необязательных** поля. Старые fixtures остаются допустимыми:

```json
{
  "research_strategy": "exploit_incumbent",
  "base_result": {
    "experiment_id": "exp-example",
    "state": "evaluated",
    "recipe_id": "linear-regressor-v1",
    "hypothesis": "Previous measured experiment",
    "metric": {
      "metric_id": "rmse",
      "direction": "minimize",
      "value": 10.0,
      "validation_id": "validation-example",
      "dataset_id": "dataset-example",
      "fidelity": "full"
    },
    "hyperparameters": {
      "alpha": 1.0,
      "target_transform": "identity",
      "numeric_interactions": false
    },
    "feature_steps": [],
    "seed": 42,
    "is_incumbent": true,
    "error": null
  }
}
```

Это фрагмент user-сообщения, а не полный `GContextUser`. `base_result` также может быть `null` до
первого результата. Его полная схема — новый `GExperimentMemory` в `contracts/contracts.schema.json`.
`facts[].summary` остаётся строкой с ограниченным JSON; в ней могут быть параметры/измерения эксперимента
или причина отказа предложения. Score появляется только из подтверждённой evaluation.

`state.sqlite` и его таблицы не заменялись; SQL-миграция для этого изменения не требуется. Решения,
контрольные точки, код, метрики и artifact hashes сохраняются прежним механизмом. Новые поля контекста
попадают в owned runtime snapshot, поэтому реконструкция использует именно сохранённую реализацию.

## Какие события читать

- `context.built`: стратегия, база, количество сохранённых/пропущенных фактов, сокращённые поля профиля.
- `search.decision`: `action`, `reason`, parameters, checkpoint evidence.
- `graph.idea_registered`: provisional/confirmed, capabilities, source/pilot, gate reasons.
- `graph.branch_forked`: родитель, checkpoint, idea, ID `accept` и `reject`.
- `graph.branch_state_changed`: pause/resume/archive и причина.
- `graph.plateau_assessed`: статус, distinct solutions, длительность, gain и epsilon.
- `research.component_transfer_prepared`: pilot/acceptance, собственная база и источник.
- `research.constraints_applied`: предложенное и реально исполненное значения.
- `search.finished`: фактическая причина остановки, не предположение об исчерпании трёх часов.

Authoritative записи по-прежнему находятся в `g_events`; `events.jsonl` и терминал — telemetry.
Просмотр: `python3 scripts/show_graph.py <run_directory>`; полный срез: тот же вызов с `--json`.

## Настройка продолжительного поиска

В присланном запуске остановка произошла после 12 исследований примерно за 4 минуты 54 секунды.
Осталось около 2 часов 55 минут. Это следствие **настроенного лимита**, а не признака того, что весь
пространство моделей исследовано. Само увеличение TIME_BUDGET_SECONDS эту настройку не меняет.

Стандартный профиль оставлен совместимым. Для следующего более продолжительного прогона:

```bash
python3 scripts/configure.py --env-file .env --profile extended
python3 scripts/configure.py --env-file .env --profile extended --apply
```

Первый вызов только показывает предлагаемые значения. Extended поднимает потолки до 100 новых
исследовательских обучений и 96 API-попыток. Уже заданный `LLM_MAX_TOTAL_OUTPUT_TOKENS`, время, ключ,
адрес API, модель и рабочие пути сохраняются. Если output-квота не задана, используется прежний default
262144. Repair/retry также расходуют API-попытки. Это потолки, а не обещание выполнить 100 обучений:
поиск может раньше завершиться по времени, output-квоте, доступности провайдера или валидности предложений.
Более длинный профиль может увеличить реальные расходы API; он применяется только явной командой `--apply`.

`GRAPH_TRAIN_WORKERS=1` теперь перекрывает последовательное обучение с ожиданием другого API-запроса.
Режим `2` сохраняет пакетное параллельное обучение. Полный непрерывный dispatcher сразу с двумя
обучениями и новыми поручениями во время fit пока не реализован.

## Следующие задачи по эффективности

1. **Контролируемые пробы после смешанного улучшения.** Сейчас transferable idea обнаруживается,
   когда подходящая пара уже измерена. Если LLM одновременно меняет новый feature и несколько
   гиперпараметров, автоматического дополнительного ablation-эксперимента ещё нет. Промпт просит менять
   одну фичу, но это не заменяет планирование. Следующий шаг — отдельное типизированное решение G14
   для controlled probe с явной собственной базой и резервом попытки; затем обычный source/pilot gate.
2. **Предметная диагностика ошибок.** Исследователь получает score, параметры и факты отказов.
   Нужны проверяемые отчёты по группам/остаткам/признакам из evaluator, чтобы поручать конкретную
   гипотезу вместо очередного общего тюнинга. Не следует давать LLM test labels или выбирать split по score.
3. **Локальный HPO внутри ветки.** Несколько контролируемых проб вокруг одной принятой гипотезы можно
   выполнять без нового LLM-запроса на каждый числовой параметр. Пока такое локальное search space
   не является согласованным выходом C09; произвольный Optuna/новая зависимость не добавлялись.
4. **Разнообразие по фактическим предсказаниям.** Нужны OOF/CV и оценка сходства ошибок, прежде чем
   объединять модели. Ensemble compiler по-прежнему явно не поддерживается в графе v1.
5. **Измерение на настоящей задаче.** Сначала повторить тот же validation protocol/seed с прежними
   лимитами, затем отдельно расширить бюджет. Это отделит эффект исправлений от эффекта числа попыток.

## Проверки

Конкретные результаты финального `scripts/check.py`, состав среды и ограничения проверки записаны в
`VALIDATION-RESEARCH.md` и `validation-research-unittest.log`. Сценарии состояния используют явно заданные
тестовые оценки. Полные ML-сценарии обучают настоящие estimator на синтетике; LLM/API там подменены.
Проверка совпадения реконструированных предсказаний, неизменности C00–C24 и читаемой платформенной
поставки входит в итоговую проверку. Live API, пользовательский датасет, CatBoost в официальном образе
и непрерывный трёхчасовой прогон в этой среде не выполнялись.
