# Реализация и соответствие ТЗ

Завершение диалогов и продвижение разрешённых серий во время API-ожидания:
[DIALOGUE-PROGRESS.md](DIALOGUE-PROGRESS.md). Budget атомарно защищает финальные запросы
и output tokens; Gateway освобождает неизрасходованные резервы в finally. Graph controller
продолжает ask/train/evaluate/tell на dispatcher, не создавая исследовательских действий.

Adaptive-тюнинг: [OPTUNA.md](OPTUNA.md). `agent/optuna_search.py` владеет ask/tell и снимками
серий в dispatcher; `agent/tuning_space.py` проверяет декларативные домены. Исследовательские
потоки не обучают модели и не пишут SQLite. Runner/Evaluator/Finalizer сохраняют прежние роли.

Актуальные исправления tool-протокола и память исследовательских решений:
[RESEARCH-DECISION-FIXES.md](RESEARCH-DECISION-FIXES.md). Артефакты решений неизменяемы;
проекция фактов/идей строится dispatcher-ом без новой таблицы и дополнительных LLM-вызовов.

Локальная библиотека опыта: [KNOWLEDGE.md](KNOWLEDGE.md). `tools/knowledge.py` выполняет
поиск по подготовленным источникам без моделей/сети/SQLite. C08 включает начальную выдачу,
C10 исполняет search_knowledge, C09 проверяет видимость knowledge_ids и сохраняет ссылки
на артефакты. Политика предобработки используется конструктором и контекстом совместно.
KnowledgeQuery и необязательный knowledge_ids добавлены во внутренние схемы;
ExperimentPlan, frozen split, независимая оценка и fit/predict остаются у прежних владельцев.

Это реализация v0.6.0 с адаптивным исследовательским интерфейсом, постоянным графом и читаемой плоской поставкой. Новая политика и её проверяемые границы: [OPEN-RESEARCH.md](OPEN-RESEARCH.md). Контракты C00–C24 и ExperimentPlan сохранены; ResearchAction-v1 и AnalysisQuery добавлены как внутренние схемы. Остальное описание исторических режимов ниже применяется к явно выбранным catalog/code. Актуальные правила поставки: `PLATFORM.md`; граф и восстановление: [GRAPH.md](GRAPH.md).

v0.5.1: [FINAL-REFINEMENT.md](FINAL-REFINEMENT.md) описывает G15, переход 85/15, фазовые квоты,
восстановление origin ветви global best и точное хранение GRefinement. Исходные C00–C24 не изменены.

## Последовательность

C01 читает Markdown и разрешает пути. C03 собирает профиль, чтобы C02 видел реальную техническую схему. C04 проверяет извлечённые значения обычным кодом. LLM отдельно предлагает протокол C05 из четырёх поддерживаемых holdout-стратегий. Каталог C06 публикует инструменты и рецепты.

Ранний Dummy проходит ту же проверку метрики, full refit и проверку формата, что дальнейшие модели. После его публикации проходят начальные испытания каталога, затем два LLM-контекста конкурентно предлагают по одному плану. По умолчанию это ResearchChoice-v1 без кода/tools; C11 сохраняет детерминированную factory-обёртку. Старый ResearchProposal-v1 сохранён для явного RESEARCH_MODE=code. Dispatcher резервирует планы транзакционно, запускает максимум два процесса и обрабатывает их события. После завершённой пачки train немедленно готовится лучший кандидат, до ожидания следующего peer или train-пачки. Это сохраняет два исследовательских потока и ограничивает расходы на лишние refit.

В v0.5 серии из нескольких связанных испытаний чередуются с новыми предложениями. `LocalSearch` меняет один параметр за раз и соблюдает ограничения текущей ветви. Повторы и отказ модели от продолжения заменяются локальными кандидатами. При ошибке ответа сохраняется факт ошибки и создаётся новое поручение для замены. Исчерпание квоты обращений или выходных токенов не завершает обучение. `DurationModel` собирает время по семействам; `Budget` проверяет прогноз обучения и запас на полный refit перед выдачей ресурсов. Числового предела обучений нет. Все изменения SQLite остаются в основном потоке; новые форматы C00–C24 или G00–G14 не добавлены.

Состояния train: queued → running → trained → evaluated; ошибки: failed/timed_out/cancelled/invalid. `best_evaluated` и `published_champion` хранятся отдельно. Финализация проходит preparing → refitting → validating → published либо явную ошибку. Её снимки находятся в `submissions/`.

## Что обеспечивает каркас

- Python 3.12; ZIP запускается с переданным путём к task.md, default — task.md.
- В платформенном ZIP корневые `solution.py`, `requirements.txt` и отдельные читаемые Python-модули с неизменённым содержимым исходников. `solution.py` копирует их в package-каталоги под `/tmp`; SQL/JSON/Markdown берутся из открытых строк `stepan_resources.py`. Сжатого или закодированного runtime в точке входа нет. Версии/полный список `requirements.txt` совпадают с исходным списком организаторов. Локальное подмножество — `requirements.runtime.txt`.
- Native API-клиент берёт ключ/адрес только из OPENAI_API_KEY/BASE_URL. OPENAI_MODEL необязателен; документированный default — qwen/qwen3.8-27b, прокси подставляет модель задачи. Fallback на другой сервис отсутствует.
- Дневной бюджет 600 RUB общий для ключа команды. Маркер `Budget has been exceeded` блокирует повторные и последующие запросы в текущем Gateway, не ожидая сброса в 03:00 МСК. Уже опубликованный проверенный результат сохраняется.
- Каждый запуск изолирован новым run_id. Перенос обученных моделей и опыта между задачами отсутствует.
- Сравниваются локальные метрики по общему dataset/protocol/fidelity. Платформа не даёт промежуточную оценку и не вызывается из исследовательского цикла.
- Дедлайн учитывает импорты, подготовку, API, train, refit и запись. Worker имеет собственные watchdog wall-time/peak-RSS, parent — наблюдение за группой и heartbeat. Более 10800 секунд в Config задать нельзя.
- Новое обучение резервирует до 3 CPU и 10 GiB. Потоки BLAS/OpenMP и n_jobs ограничены. Два задания используют до 6 CPU / 20 GiB, оставляя запас общей среде 8 CPU / 32 GB.
- RAM watchdog — периодическая проверка RSS, не отдельный kernel-cgroup на каждый job. Общий жёсткий предел обеспечивает платформа или `docker run --memory/--cpus`.
- Runner создаёт отдельную группу процессов. C24 подтверждает остановку до освобождения ресурсов. Ключи API не входят в окружение обучения.
- CSV проверяется по числу строк, точным колонкам, текстовому порядку id, допустимым классам и конечности чисел. Ведущие нули id сохраняются.
- Готовый CSV заменяется атомарно через temp того же каталога. Он доступен для чтения evaluator-процессу. SQLite/filesystem не объявляются общей транзакцией: publication journal закрывает окно сбоя после replace.

Один запуск принимает одно условие. Явные существующие пути из task.md имеют приоритет, затем для train/test выбираются файлы рядом с условием. Если их нет, поиск стандартного имени допускается только при единственном совпадении внутри task root, без `.venv`, `.git`, `runs/` и других служебных каталогов. Необязательный sample_submission/data_dictionary ищется только у выбранных данных либо рядом с условием. Неоднозначность и выход за task root возвращают ошибку. `scripts/list_tasks.py` перечисляет условия и проверяет только наличие/однозначность путей.

## Проверка кода и метрики

Generated code содержит `make_pipeline(task_spec, params)`. Runner передаёт `_cpu_threads` и `_seed`, ограничивает параметры потоков и владеет fit/predict. Условие, evaluator и итоговый файл исследователь не изменяет через объявленные инструменты. AST-проверка ограничивает импорты и очевидные опасные вызовы, но не является OS-песочницей произвольного Python. При дальнейшем расширении генерации изоляция проектируется отдельно.

Метрика рассчитывается по предсказаниям evaluator-кодом, а не принимается из текста LLM. Индексы split и реализация оценщика входят в hash протокола. Пропуски входных признаков — только пустые ячейки; строковая категория `NA` сохраняется.

Fingerprint содержит версию данных/задачи/валидации/рецепта, фактические параметры с defaults, hash кода, feature_steps, seed и fidelity. Отпечатки исключают researcher_id и словесную гипотезу. В v0.1 дедупликация точная; семантически эквивалентный Python с другим исходным текстом может получить другой hash.

## Уточнения исходной схемы

- Логический C21 idempotency key включает experiment_id и hash кандидата: два разных эксперимента могут дать одинаковый CSV при разных валидационных оценках.
- C19 соблюдает output_relative_path; все промежуточные пути остаются внутри run workspace.
- Полный C03-профиль и data_dictionary сохраняются артефактом; LLM получает ограниченную сводку. Усечения фиксируются явно.
- Вложенные вызовы получают parent_span_id. Полные модели и таблицы не проходят через JSON/LLM.
- Работа возобновляется новым run_id, без автоматического resume старого исследования. Publication journal поддерживает согласование записи в рамках того же run, если файл уже заменён.
- Ошибка live API после baseline завершает поиск с проверенным готовым ответом и state=degraded. Ошибка до проверенного ответа возвращает ненулевой exit code.
- Источники task/metric ограничены текущим ТЗ, схемой и входными файлами. Неподдерживаемый формат не подменяется знакомым.

## Следующие независимые задачи

A: очередь с более гибким backpressure, persisted retry attempts, дополнительные контроли процессов.
B: анализ ошибок по артефактам, улучшение diversity поручений, более точный подсчёт контекста при доступном tokenizer сервиса.
C: CV, OOF-ансамбли, дополнительные метрики/форматы ответа, новые проверяемые преобразования признаков.

MCP не используется и не требуется. Это снимает зависимость от неявной установки mcp в baseline. Несовпадение путей архива обрабатывает task-local resolver. Raw API и CatBoost нужно отдельно прогнать в среде организаторов; endpoint и rate limits не выдумываются.

## Реализовано в v0.3

C00–C24 и ExperimentPlan остаются совместимыми. C10 принимает новый внутренний ResearchChoice-v1;
его producer/consumer и schemas создаются совместно в context.py/researcher.py. Каталог recipes-v2
добавляет ExtraTrees, управляемый target_transform и более широкий проверяемый диапазон итераций.
Обе ветки получают разные семейства относительно настоящего incumbent; семантически одинаковые
параметры каталога имеют одинаковый код и точный fingerprint. Ошибки/дубли/честная метрика не подменяются.

Output truncation отделён от полных schema-ошибок и повторов tool_calls. Незавершённый JSON/
одиночные незавершённые arguments на достигнутом cap могут повысить cap до клиентского потолка;
повтор на том же потолке не тратится. Полный валидный ответ принимается и при length. Значения провайдера usage сохраняются фактически, даже если
reasoning_tokens > completion_tokens: это отмечается usage_inconsistent, не исправляется догадкой.
Токен-квота отдельна от BudgetSnapshot wire-схемы: token_snapshot используется в логах/summary.
Параллельные API-запросы резервируют max_tokens атомарно. Без usage полная резервация консервативно
списывается в output_charged, а output_reported не выдумывается.

Worker строит estimator, проверяет доступные sklearn parameter constraints и лишь затем запускает fit.
В кодовом режиме это дополнительная ранняя проверка, а не гарантия корректности произвольного Python.
Промежуточные стадии worker передаются в терминал через ограниченный redacted stdout-протокол.
Источником завершающего статуса по-прежнему служит result.json и подтверждённая остановка процесса.

## Завершение процессов v0.3.1

Runner.poll сначала проверяет выход основного worker, затем останавливает оставшиеся процессы
его группы через общий внутренний механизм SIGTERM → ограниченное ожидание → SIGKILL.
Служебная очистка завершившегося worker не устанавливает forced_state. Успех требует exit code 0
и success=true в result.json; ошибка или отсутствие результата остаются ошибкой. Только после
остановки группы формируются прежний C15 и C13 release. При PROCESS_STOP_FAILED lease остаётся
занятым. C24 и его JSON-схемы не изменились: это явная отмена работающего задания или таймаут.
Проверка heartbeat больше не отменяет worker, успевший завершиться между двумя poll.

В Linux с procfs, смонтированным из родительского PID namespace, NSpid сопоставляет локальные PID
реальным путям /proc. Перед сопоставлением проверяется namespace процесса. RSS читается по тем же
путям, поэтому живые дочерние процессы учитываются даже после выхода основного worker.

## Граф v0.4

Исходные C00–C24 и их закрытые JSON-схемы сохранены. G00–G15/I00–I03 добавлены в тот же ContractBus.
Основной цикл — agent/graph/controller.py; single-writer facade — agent/graph/service.py. Все SQL
используют существующую state.sqlite. Store.transaction применяет SAVEPOINT при вложении;
reserve_tx/commit_evaluation_tx не коммитят внешние T4/T5. В одной транзакции фиксируются native
reservation/selection, graph projection, event и durable idempotency response. Publisher остаётся C18–C21.

Графовый catalog mode принимает только точный owned factory. Code mode остаётся явным; свободный
Python не сертифицируется для hard-restricted ветви. Дополнительный переносимый компонент
numeric_interactions строит квадраты/произведения не более первых восьми числовых столбцов,
выбранных на fit-строках. Он добавляет до 36 колонок и входит в рецепт, manifest и component trial.
target_transform/class_weight имеют отдельные capabilities. Обычный тюнинг параметров создаёт
версию нижнего DAG, а не командный fork.

Owned runtime, фактические package versions, code/params/seed/protocol сохраняются для реконструкции.
scripts/reconstruct_solution.py проверяет hashes, извлекает собственный runtime и создаёт refit job;
само обучение запускается отдельно. Исходные данные, пакеты и предобученные веса в архив не входят.


## Дополнение v0.4.3

G02 сохраняет причинный pre-idea checkpoint, но явно выбирает собственные измеренные стартовые базы
детей по совместимости с их constraints. Выбор ограничен знанием родительской линии до selection_cut,
а не global best. GBranchSeed связывает head, parent, checkpoint и cut; producer G02, consumers
WorkService.visible_history, G07 и G11. Собственные поздние результаты родителя разрешены только
через эту явную ссылку; история siblings не добавляется.

Начальные конфигурации одного рецепта сохраняют владельца; сначала измеряются обычные базы,
затем feature-варианты. Точное совпадение следующего warmup с patch на базе другого peer становится
recipient pilot без дополнительного API/обучения. Остальные warmups остаются обычными trials.

G07 требует четыре разных полных решения подряд без существенного суммарного улучшения,
и прежний минимальный интервал времени. Малые улучшения накапливаются относительно фиксированного
anchor; любое улучшение обновляет C17/head независимо от epsilon плато. G03 выдаёт каждому peer
три exploit на один explore. Evaluator передаёт ограниченные агрегаты ошибок по группам/классам;
C00–C24 не меняются. Snapshot весов необязателен, сжат и ограничен по отдельной модели и всему запуску.

## Исправления согласованности v0.5.2

Разбор реального запуска и полный перечень изменений: [RUN-REVIEW-ab9dbc6c.md](RUN-REVIEW-ab9dbc6c.md). Таймаут C10 ограничивает ответ LLM, TTL поручения оркестратора покрывает очередь до общего deadline. Доноры выбираются по всей родительской линии с проверкой запретов. Частичные параметры доработки накладываются на измеренную базу в обеих фазах.

`profile_summary.measured_search` содержит ограниченные записи старых предложений и лучших вариантов семейств без повторяющихся diagnostics. `LocalSearch` чередует оси и выбирает допустимую измеренную базу перед каждым продолжением. В финальной фазе фиксируются только feature switches; enum модельных параметров остаются доступны. GPlateau получил optional `peer_trials_since_progress`: для выхода по плато нужны четыре разные оценки каждого peer после прогресса/возобновления. Старые C00–C24 не менялись.

Временная граница поиска фиксирована по output reserve, а допуск нового fit проверяет и фазовый остаток. G14 может начать доводку раньше границы, если прогноз следующей партии уже не помещается. Прогноз не является гарантией длительности обучения. Обычный BACKTRACK сохраняет paused-ветвь; только новый fork может атомарно архивировать проверенную paused-ветвь для размещения обоих детей.

В рамках этого изменения тесты не запускались по просьбе пользователя.
