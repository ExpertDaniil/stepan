Архив: `run-20261022T091615Z-3c154043.zip`. Все **51 runtime-файл** внутри архива побайтово

## Что действительно произошло

- State `completed`, elapsed по `summary.md` — **237,70 с**. Было 13 различных экспериментов:
  Dummy + 4 начальные конфигурации + 8 новых LLM-конфигураций. Все получили валидные оценки.
- 11 API-вызовов: два bootstrap и девять исследовательских предложений. Одно предложение повторило
  уже измеренную конфигурацию и было использовано из кеша. Нулевые ошибки/отклонения предложений.
- Созданы root, accept и reject. Родитель sealed; accept paused; reject active.
- Ни одно из семи G07-измерений не вернуло `plateau`: только `searching`/`insufficient_evidence`.
- Переход accept → reject произошёл по **резерву попытки альтернативы перед лимитом**, не по epsilon.
- Остановка `experiment_limit`: израсходованы 12 из 12 исследовательских обучений. В снимке бюджета
  оставались 10562 с, 21 API-вызов и 234829 выходных токенов. Трёхчасовой лимит не был причиной.
- Лучший и опубликованный результат — **HGB + shifted_log1p, RMSE 44,922615**, найденный в warmup.
  Новые LLM-конфигурации его не улучшили. Финальный CSV не заменялся худшей моделью.

дообучение для произвольного такого предложения пока не реализовано.

Точная причина ухудшения качества отдельной модели не определяется по одному validation score.
Например, рост ошибки при 2000 итерациях совместим с переобучением, но train score/кривые обучения
в этом архиве этого не доказывают. Утверждать, что сама задача уже достигла плато, также нельзя.

## Найденная причина потери направления

Причинный checkpoint идеи `target_transform` был создан до первой начальной пары. Обе его головы —
Dummy. После подтверждения фичи G02 честно восстановил этот слишком ранний snapshot для обоих детей.
Получилась потеря рабочих баз: глобальный лучший HGB был сохранён для финального выбора, но peers
в новой ветке снова видели Dummy как собственную отправную точку. Перенести фичу на Dummy нельзя.
Началось повторное исследование семейств, включая Ridge, вместо последовательной доработки
сильных собственных моделей. Проверки памяти v0.4.2 передавали состояние корректно; плохо было
выбрано само состояние, с которого агент продолжал работу.

Дополнительно старое чередование примерно 50/50 слишком часто отправляло каждого peer в другое
семейство. Агрегатных ошибок по группам/классам в исследовательском контексте не было: объяснения
про недообучение и увеличение модели опирались главным образом на догадки.

## Что изменено

1. **Старт ветвей.** Причинный checkpoint не переписывается. G02 отдельно выбирает каждому peer
   лучший собственный измеренный full результат родительской линии, допустимый в ребёнке.
   GBranchSeed явно фиксирует parent, checkpoint, selection_cut, head и причину. Чужой global best
   автоматически не копируется. Для accept без подходящего результата сохраняется собственная
   база без фичи, после чего работает controlled transfer. Ошибки, недоверенные оценки и
   непроверенный Python под hard constraints не становятся допустимыми стартовыми решениями.
2. **Начальные конфигурации.** Сначала оба peer получают обычные базы, затем их feature-варианты.
   Владелец одной численной конфигурации сохраняется между её вариантами. Если следующий warmup
   точно равен переносу фичи на собственную базу другого peer, он сразу выполняется как recipient
   pilot. Это не требует отдельного API-запроса или дополнительного обучения.
3. **Исследователи.** На каждого равноправного peer — три exploit на один explore. Счётчик зависит
   от его завершённых поручений, а не от проходов цикла/fork. В exploit инструкция предлагает
   начинать с точных параметров своей базы и менять не больше двух; это подсказка модели, не
   новый жёсткий запрет на пространство гипотез. Для другого семейства стартуют от его defaults.
4. **Обратная связь.** Evaluator сохраняет до четырёх групп с большой ошибкой; в классификации —
   до шести классов из ограниченного обзора. Параметры групп определяются по fit-части, ошибки —
   на прежнем holdout. В контекст попадают агрегаты, без построчных labels и без матрицы N×N.
   Это помогает выбирать следующую гипотезу, но не является гарантией прироста качества.
5. **Плато.** По умолчанию нужны четыре разные full solution подряд без существенного суммарного
   улучшения и прежние 300 секунд без существенного прогресса после активации ветки. Малые gains
   складываются относительно фиксированного anchor; при превышении epsilon счётчик сбрасывается.
   Exact cache, повтор другого seed той же solution, failed и archived late results не создают
   ложную серию плато. Любое настоящее улучшение по-прежнему может обновить head/CSV.
6. **Переходы по бюджету.** Обычное переключение accept по доле бюджета ждёт минимум window
   испытаний текущей линии. Перед жёстким исчерпанием попыток аварийный резерв альтернативы
   остаётся: ресурсный лимит не превращается в ложный диагноз `plateau`.
7. **Размеры файлов.** Веса сохраняются с joblib compress=3: до 16 MiB на снимок и 64 MiB за запуск,
   с резервированием места одновременно работающим процессам. Лимит останавливает запись и
   удаляет partial-файл, а fit/predict остаётся успешным. stdout/stderr ограничены по 1 MiB именно
   в UTF-8 байтах; поток продолжает дренироваться. Все эти limits настраиваются.
8. **Анализатор.** `analyze_run.py` показывает размеры весов, CSV, worker logs и прочих данных плюс
   крупнейшие файлы. `graph-events.jsonl` больше не определяется как второй самостоятельный run.

## Почему это не слишком большая дельта

В архиве relative epsilon = 0,001: возле RMSE 45 это примерно **0,045 RMSE**. Этот порог использовался
для решения о плато, а не для отклонения модели или запрета улучшить CSV. В этом запуске плато
вообще не сработало. Поэтому просто уменьшить epsilon было бы исправлением другой проблемы.

Новый G07 явно показывает consecutive_no_gain / required_no_gain. Например, RMSE
100 → 99,97 → 99,94 → 99,91 → 99,88 даёт суммарное улучшение 0,12, превышает epsilon 0,1
и сбрасывает серию, хотя каждый отдельный шаг меньше порога. Четыре ухудшения после известной
базы при достаточном времени дают плато; три — ещё нет. Absolute и relative epsilon теперь
доступны отдельно в env. Статистическая значимость этим инженерным правилом не доказывается.

Примерно 55% объёма занимают веса. Раньше любой обученный estimator, в том числе большой лес
классификации, записывался целиком без сжатия и без общего лимита. Это подтверждённый путь роста
каталога runs, который исправлен. Но архив классификации на 3 ГБ не предоставлен, поэтому нельзя
утверждать, что все его 3 ГБ — именно веса. Новый анализатор позволит установить это по фактам:

```bash
python3 scripts/analyze_run.py /path/to/classification-run.zip --json
```

Полного фиксированного предела на весь run нет: исходные размеры CSV, число сохранённых кандидатов,
API snapshots и валидные журналы отдельно влияют на объём. Граф/метрики/предсказания не удаляются
ради произвольного общего лимита; это сохраняет проверяемость и реконструкцию решения.

## Как применить

```bash
git pull
python3 scripts/configure.py --env-file .env --profile extended --apply
```

Это выставляет window=4, exploit_steps=3, ограничения файлов и **до 100 обучений / 96 API-попыток**
вместо 12/32. Ключи, URL, модель, пути и время сохраняются. Уже заданная общая output-квота
сохраняется; дневной/провайдерский бюджет также остаётся ограничением. Process env имеет приоритет
над `.env`. Одного git pull недостаточно, если в старом `.env` остались 12 попыток и window=3.
Для отключения необязательных весов можно задать MODEL_SNAPSHOT_MAX_BYTES=0.

Больше попыток не гарантирует ровно три часа или лучший RMSE. Сначала полезно сравнить версии на
одинаковом split/seed/бюджете, затем отдельно оценить эффект расширенного бюджета.
