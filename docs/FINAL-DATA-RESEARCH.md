## Почему поиск мог выглядеть как перебор среднего и гиперпараметров

1. Исторический `catalog` разрешал только готовые рецепты и переключатели. Ни
   длинный ответ, ни более подробный промпт не добавляли недоступные действия.
2. В новых adaptive-контекстах всё ещё предлагался Dummy. Он нужен для раннего
   корректного CSV, но настройка среднего/majority не является развитием модели.
3. Собственная база peer могла быть намного слабее уже измеренного решения
   другого peer. Теперь передаётся отдельный сопоставимый research landscape;
   собственный head и происхождение версий при этом сохраняются.
4. Инструкция разрешала новые признаки в refinement, а G04 их отклонял. Для
   adaptive снята legacy-блокировка семейства/переключателей. Явные ограничения
   намеренно созданной ветки и проверка frozen manifest сохранены.
5. Случайная выборка до запроса теряла редкие группы. Первые 128 столбцов профиля
   не давали исследовать остальную схему. Объединён потоковый доступ с фильтрацией
   до выборки, пагинацией схемы и диагностикой исключённых идентификаторов.
6. После сокращения API-контекста удалялись `train_columns`, а обработчик features
   требовал это поле. Полная схема теперь сохраняется у Researcher на стороне
   контроллера; компактация не отменяет проверку существования/допустимости входов.
7. Оценка нескольких числовых целей падала при `float(np.std(DataFrame))`.
   Метаданные агрегируются по явному NumPy-массиву; все цели исключены из групп
   диагностики и запросов анализа.

Это наблюдаемые ограничения/ошибки системы. Они не доказывают, что любая неудачная
гипотеза вызвана инфраструктурой, или что качество самой LLM теперь гарантировано.
Исходный журнал нового эпизода со «средним» не предоставлен; его точную причину
нельзя восстановить только по сообщению из командного чата.

## Что исполняется в новой версии

Сохраняется adaptive-цикл из open: запрос fit-only анализа, выбор features/custom
pipeline/model/tune, обычные Runner/Evaluator, обратная связь и проверенная
публикация. Существующие исследователи получают вращающиеся задания по признакам;
нового LLM-критика или постоянно закреплённых ролей не добавлено.

- Программы включают индикаторы пропусков, безопасные преобразования, арифметику,
  частоты/пересечения категорий, групповые статистики и даты. Частоты и групповые
  распределения подгоняются на fit и не пересчитываются по validation/test batch.
- Произвольная разрешённая предобработка и отбор столбцов доступны через custom
  `make_pipeline`. Одно лишь описание `feature_steps` не считается доказательством
  исполнения преобразования.
- Механический tuning остаётся ограниченной явно разрешённой Optuna-серией.
  Dummy запрещён в adaptive catalog/tune и не предлагается в меню исследований;
  ранний аварийный ответ сохраняется. Custom-конвейер не классифицируется как
  «обучаемый» по названию класса: фактически постоянные предсказания видны в
  `prediction_behavior`, без автоматического запрета легитимных константных задач.
- `research_landscape` содержит сильнейшую измеренную обучаемую конфигурацию,
  лучшие по семействам и число выполненных программ признаков. Все ссылки из
  показанных проекций принимаются проверкой provenance; невидимые ID запрещены.
- Анализ возвращает fit-only средние/разброс/квантили и групповые сводки. Фильтр
  нельзя строить по любой целевой колонке. Диагностический доступ к ID не включает
  его в модель. Не более 20 тысяч выбранных строк плюс CSV-чанк находятся в
  выборке запроса; чтение/фильтрация проверяет сроки кооперативно.
- IO guard доверяет объекту штатного watchdog-thread, а не подделываемому имени.
  Новые owned-модули входят в читаемый плоский пакет и frozen runtime.
- `scripts/analyze_run.py` показывает число анализов, реально оценённые программы
  признаков, действия LLM и результаты по рецептам. Старый журнал без timestamps
  читается с явным «время неизвестно», без придуманного wall time.

Конечный выбор опирается на метрики контроллера. Заявление LLM о причине улучшения,
отсутствии перспектив семейства или полезности отдельного признака не превращается
в установленный факт. Совместное изменение оценивает весь pipeline; оно не доказывает
эффект каждого компонента. Новые программы могут оказаться бесполезными или ухудшить результат.

## Запуск для команды

Из рабочего дерева новой ветки, в заранее подготовленном разрешённом окружении:

```bash
RESEARCH_MODE=adaptive FEATURE_RESEARCH_ENABLED=1 python3 solution.py "путь/к/задаче/task.md" --env-file .env --profile platform
```

Явные переменные процесса приоритетнее старого `.env`, где мог сохраниться
`RESEARCH_MODE=catalog`. Ключ и endpoint берутся из предоставленного окружения;
они не входят в ZIP. Runtime не устанавливает пакеты и не загружает модели.
Проверьте, что используются предусмотренные организаторами зависимости, включая
Optuna, прежде чем начинать трёхчасовой прогон.

После запуска:

```bash
python3 scripts/analyze_run.py runs/run-... --json
```

Оценивайте завершённые эксперименты, новые представления, ошибки, время без jobs
и подтверждённый итоговый pipeline. Число токенов, красивое объяснение или количество
конфигураций сами по себе не являются мерой качества исследования.
