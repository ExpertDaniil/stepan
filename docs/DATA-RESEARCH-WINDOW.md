# Сначала данные, затем подбор параметров

В `adaptive` по умолчанию включён обязательный начальный этап анализа и обработки
данных. На трёхчасовом запуске он длится **1800 секунд**, на коротких — одну шестую
общего бюджета, с округлением вниз до целых секунд и минимумом в одну секунду.
Верхняя граница автоматического значения — 1800 секунд.

Таймер начинается **после** стартового проверенного ответа и начальных обучаемых
моделей. Он один на запуск: параллельная работа двух исследователей не удваивает
зачёт, переход на другую ветку и повторный вызов старта не сбрасывают отсчёт.
Общий трёхчасовой срок при этом не увеличивается.

## Что доступно в начальный период

| Действие | До конца обязательного этапа | После |
|---|---|---|
| Дополнительный анализ обучающих данных, чтение памяти и местных материалов | Доступно | Доступно |
| `features`: исполняемая программа признаков | Доступно с фиксированными модельными параметрами | Доступно |
| `pipeline`: собственная обработка данных | Нужен явный непустой список `feature_steps` | Доступно по общим правилам |
| `catalog`: отдельная модельная конфигурация | Закрыто после стартовых моделей | Доступно |
| `tune`: серия Optuna | Закрыто | Доступно |
| Автоматический резервный перебор при недоступном API | Закрыто | Доступно по прежним правилам |
| `stop`: закончить исследования из-за достаточного решения | Закрыто | Доступно |

Для `features` модельные параметры фиксированы на значениях рецепта по умолчанию
с учётом явных ограничений ветки. Передайте `hyperparameters={}`. Отдельно можно
менять переключатели обработки `numeric_interactions` и `target_transform`.
Таким образом, повтор одного преобразования с разными `alpha`, глубиной или числом
деревьев не превращается в разрешённый перебор под именем `features`.

У произвольного `pipeline` контроллер требует объявленные шаги обработки; их
названия сами по себе не доказывают смысл Python-кода. Система сохраняет исходник
и реально измеряет весь опыт. Универсального доказательства семантики программы
эта временная политика не вводит.

Когда время этапа истекло, Optuna и модельные опыты автоматически открываются.
Отсутствие улучшения не требуется подтверждать искусственным порогом метрики.
Полезные исследования данных можно продолжать и после первых 30 минут.

## Где действует ограничение

- `Budget` ведёт единый монотонный таймер; его снимок не меняет стандартную
  обёртку `BudgetSnapshot` C00–C24.
- `ContextBuilder` передаёт фазу, остаток времени и обязательное поручение.
  Поле `data_research` остаётся в профиле при сокращении контекста.
- `Gateway` заново проверяет текущее состояние при отправке. В начальный период
  схема ответа разрешает только `features/pipeline`; сохранённый старый контекст
  не открывает настройку раньше срока.
- `Researcher` и диспетчер независимо проверяют принятый тип действия и параметры.
  Модельный опыт без изменений данных не получает допуск к запуску процесса.
- `OptunaSearch` не создаёт новую серию и не предлагает точки уже существующей
  серии, пока этап закрыт. `LocalSearch` и `local_plan` не обходят запрет через
  резервные каталожные конфигурации.
- Начальная фаза не переключается в окончательную доводку по обычной эвристике
  `refinement_due`, пока действует обязательное окно данных.

Никаких ожиданий ради заполнения таймера нет: исследователи анализируют данные
и проводят допустимые опыты. Отдельный сложный распорядитель гипотез не добавлен.

## Сроки и недоступные ресурсы

Общий срок, память, процессоры, квоты API и запас на окончательное обучение
важнее минимального исследовательского окна. При отсутствии возможности
продолжить запуск сохраняет последний проверенный ответ и явно фиксирует
`research.data_phase_interrupted`. Подбор параметров от этого не открывается.

Это означает, что при исчерпании API, ошибках или нехватке времени нельзя
обещать фактические 30 минут полезной работы. Такие запуски не помечаются как
выполнившие минимум. Зачёт времени замораживается до полного окончательного
обучения; его длительность не используется, чтобы задним числом заполнить квоту.

При нормальном ходе `research.data_phase_completed` означает, что отсчёт достиг
минимума. Это время защищённого исследовательского этапа, включая запросы анализа,
ожидание ответов и обучение проверяемых преобразований, а не сумма CPU-секунд.
События содержат наблюдаемые факты, не скрытые рассуждения модели.

## Настройки и совместимость

```bash
# Автоматически: 30 минут на трёхчасовой бюджет.
TIME_BUDGET_SECONDS=10800 python solution.py /path/task.md --env-file .env

# Явные 10 минут для отдельного опыта.
DATA_RESEARCH_MIN_SECONDS=600 python solution.py /path/task.md --env-file .env

# Явное отключение для сравнения с прежним поведением.
DATA_RESEARCH_MIN_SECONDS=0 python solution.py /path/task.md --env-file .env
```

Если переменная не задана, используется автоматическое значение. Явное значение
должно быть меньше общего бюджета; отрицательные и нецелые значения отвергаются.
`catalog/code` сохраняют прежнее поведение: они не имеют полного адаптивного
интерфейса работы с данными. Ограничение числа обучений не вводится.

Публичные типы действий, сохранённые форматы опыта, независимая оценка и выбор
проверенного ответа сохранены. Для каждого запроса используется отдельная копия
схемы; ограничение действий не изменяет глобальную схему и не протекает между
запусками. Платформенная упаковка автоматически включает новый собственный модуль.

## Проверка

`tests/test_data_research_window.py` проверяет точную границу 1800 секунд без
ожидания получаса, общий таймер для повторных вызовов, короткие бюджеты, отключение,
сохранение общего срока, запрет обхода через Optuna/резервный поиск, фиксацию
параметров, контекст/схему ответа и незачёт окончательного обучения.
Сквозной сценарий действительно обучает преобразование признаков и затем
запускает разрешённую серию Optuna, проверяет CSV и согласованность SQLite.
API в этом сценарии явно имитируется; качество решения соревнования не измеряется.

Перед публикацией целевой набор прошёл **14/14 за 16,894 секунды** в Ubuntu,
Python 3.12, на разрешённых закреплённых версиях основных библиотек.

Полный набор запускается **после публикации** изменений в `feat/final-data-research`
по запросу команды. Его фактический результат будет добавлен отдельной записью;
наличие новых тестов само по себе не означает, что весь проект прошёл проверку.
