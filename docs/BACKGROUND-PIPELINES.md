# Исполняемые версии и фоновая настройка

В adaptive graph-режиме по умолчанию включён `BACKGROUND_TUNING_ENABLED=1`.
Исследователь отправляет код `make_pipeline(task_spec, params)`; фиксированный
Runner проверяет исполнение и получает предсказания, Evaluator самостоятельно
рассчитывает метрику. Фоновый сервис Optuna принадлежит версии pipeline, а не
поручению исследователя. Исследователь продолжает анализ во время обучений.

## Файл решения

```python
from agent.ml import build_pipeline

DEFAULT_PARAMS = {'alpha': 1.0}
SEARCH_SPACE = {'alpha': {'type': 'float', 'low': 0.01, 'high': 100.0, 'log': True}}

def make_pipeline(task_spec, params):
    return build_pipeline('linear-regressor-v1', task_spec, params)
```

Это пример интерфейса для регрессии, не выбор модели для любой задачи.
Обе декларации — literal dict; они извлекаются через AST без исполнения модуля.
Имена осей должны существовать в эффективных параметрах. Для своего estimator
служебные `_cpu_threads`/`_seed` нужно извлекать или фильтровать перед `**kwargs`.
Код без SEARCH_SPACE проходит первую оценку, но не получает выдуманный диапазон.
У известных рецептов диапазоны берутся из каталога. В именованных программах
признаков Optuna меняет только вложенные параметры модели, сохраняя программу.

Первой проверке предшествует fit/predict на <=2048 FIT-строках с отдельным
30-секундным watchdog этапа. Это не метрика и не обученное состояние для полного
опыта: затем pipeline создаётся заново. Ошибка становится сохранённым traceback
и feedback исследователю. Проверки не требуют investigation/test_plan/research_notes;
новый промпт ставит работу с исполняемым решением выше обслуживания параметров.

## Приоритеты и остановки

- Каждая новая версия сначала получает независимую полную оценку по общему split.
- Если её initial score лучше best score предыдущих версий с учётом
  BACKGROUND_SWITCH_MARGIN, предыдущие слабейшие серии приостанавливаются;
  выполняемые trials отменяются с остановкой группы процессов до освобождения lease.
- Более слабая новая версия получает небольшой бюджет проверки, старый лидер
  продолжает работу. Работает не более MAX_WORKERS процессов; остальные версии
  сохраняются в очереди. Возврат к претендентам чередуется с усилением лидера.
- Новая initial-проверка имеет приоритет перед фоновым trial. При необходимости
  последний прерывается; отмена не получает фиктивную плохую метрику.
- Старые лучшие результаты, код и полная история Optuna сохраняются в pipelines/.
  Начальная измеренная конфигурация импортируется в study без повторного fit,
  если она входит в пространство. TPE получает n_startup_trials=4.
- API timeout не отменяет завершённые анализы: их видимость определяется выданным
  поручением и временем результата относительно fork cut, а не наличием финального G04.
- Исследование и настройка завершаются по глобальному бюджету с резервом на CSV,
  либо когда исчерпаны и исследователи, и доступные серии. Два checkpoint сами по
  себе не закрывают поиск. Четыре одинаковых checkpoint без новых анализов
  приостанавливают peer до обновления; явный stop уважается до новых результатов.

## Ресурсы

Слоты выдаются отдельным заданиям. Общий CPU budget — до 7 логических CPU с
учётом affinity/cgroup; 1 CPU сохраняется доступным для fit-only анализа.
Один worker получает до BACKGROUND_CPU_THREADS, несколько делят бюджет.
RAM ограничена минимумом 28 GiB и 80% физического/cgroup лимита. Per-job предел
остаётся TRAIN_MEMORY_MB. Память анализа учитывается отдельно. Watchdog RSS и
лимиты потоков — кооперативные ограничения, общий hard limit обеспечивает среда.
При маленьком локальном cgroup стартовые запросы памяти также уменьшаются.

Контроллер создаёт типизированные background work orders, которые не занимают
research peer и не меняют его head во время диалога. Они используют прежние
G04/C12/Runner/C16/G05, provenance, общий независимый evaluator и защиту CSV.
В режиме версий граф хранит lineage/результаты; G14 не завершает версию из-за
отсутствия очередного fit у исследователей. SQL остаётся в dispatcher thread.

## Настройки

```dotenv
RESEARCH_MODE=adaptive
RESEARCH_PROTOCOL=compact
BACKGROUND_TUNING_ENABLED=1
BACKGROUND_MAX_TRIALS=128
BACKGROUND_TRIAL_SECONDS=300
BACKGROUND_CPU_THREADS=6
BACKGROUND_SWITCH_MARGIN=0
DATA_RESEARCH_MIN_SECONDS=0
```

Новые настройки имеют эти defaults. Для обычного запуска менять старый .env не
требуется, если он использует adaptive/compact. `BACKGROUND_TUNING_ENABLED=0`
или явный `RESEARCH_PROTOCOL=legacy` сохраняет предыдущий цикл. Новый режим
рассчитан на GRAPH_ENABLED=1; catalog/code остаются совместимыми.

Результаты анализов адресуются через analyses_index, analysis_result/ARTIFACT_ID
и analysis_code/ARTIFACT_ID. Исходники не копируются дважды в читаемые отчёты.
research.checkpoint_saved отличается от research.stop_requested.
pipeline.version_registered / execution_started / execution_preempted /
leader_replaced описывают решения фонового сервиса. Полные снимки содержат
параметры, значения и состояния trials; pipeline_search в контексте — компактная сводка.

## Проверка этого изменения

По указанию пользователя полная suite и длительные live-Qwen запуски не выполнялись.
Выполняются компиляция, точечные state/schema-тесты и короткие синтетические
проверки настоящих fit/evaluate/refit с воспроизводимыми ответами модели.
Это проверка исполнения архитектуры, не доказательство роста ML-качества.

Точечная проверка: 9/9 tests.test_pipeline_background; компиляция agent/tools/scripts;
статическая проверка официальных зависимостей и схем; короткие scripted проверки
регрессии и классификации с настоящим исполнением кода и CSV. Подробности: [validation-background-pipelines.json](validation-background-pipelines.json).
