# AutoML Agent · v0.5.2 — Research Graph

Запускаемый каркас для команды из трёх человек. Согласованные C00–C24 реализованы как внутренние Python-вызовы с проверяемыми JSON-обёртками. Платформе передаётся ZIP с `solution.py` в корне; отдельный HTTP-сервер не нужен.

v0.5.1 делит доступное время поиска на 85% исследования ветвей и 15% доводки измеренного global best.
Оба peer получают его базу и дальше независимо улучшают своё решение; в этой фазе плато не вызывает
возврат к альтернативе. Под доводку резервируются API-вызовы и выходные токены. Поиск не ограничен числом обучений;
после исчерпания API он продолжает локальные серии с прогнозом длительности fit/refit.
Основа сохранена: [docs/TIME-SEARCH.md](docs/TIME-SEARCH.md).
Порог плато в поиске — 900 секунд и по четыре разные завершённые попытки от каждого исследователя после прогресса/возобновления.
Перед границей фаз проверяется прогноз следующей партии; новый fit должен помещаться в поисковую фазу. Уже запущенный fit ограничен своим общим lease; глобальные лимиты обязательны. Подробности: [docs/FINAL-REFINEMENT.md](docs/FINAL-REFINEMENT.md).

v0.4.3 сохраняет измеренные собственные базы при fork, связывает начальные обучения с controlled transfer,
даёт каждому peer три доработки на одну проверку другого семейства и считает плато по четырём
разным попыткам с накоплением малых улучшений. Веса сжаты и ограничены 16 MiB на модель / 64 MiB
на запуск; stdout/stderr — по 1 MiB. Разбор реального запуска и ограничения проверки:
[docs/RUN-REVIEW-20261022.md](docs/RUN-REVIEW-20261022.md).

Первый проход создаёт проверенный базовый `submission.csv`, затем проверенные рецепты проходят начальные испытания, а два равноправных исследователя работают от собственных баз и контекстов. Граф хранит версии решений, перенос компонентов, ветви принятия/отклонения идеи и снимки команды. Метрики считает независимый оценщик. Обновление итогового файла выполняет единственный Publisher. Все запросы, ответы, код, контексты и переходы состояний оставляют трассировку.

Граф включён по умолчанию. Руководство, точные маршруты G00–G15/I00–I03, ограничения и восстановление: **[docs/GRAPH.md](docs/GRAPH.md)**. Прежний цикл доступен через `GRAPH_ENABLED=0`; контракты C00–C24 сохранены.

v0.5.2 исправляет доноров вложенных reject-ветвей, наследование параметров, ожидание готовых предложений и архивирование ветвей. Локальные серии чередуют параметры и используют измеренную обратную связь; компактная память сохраняет старые предложения. Разбор запуска и ограничения проверки: [RUN-REVIEW-ab9dbc6c.md](docs/RUN-REVIEW-ab9dbc6c.md).

## Быстрый локальный старт

Нужен Python **3.12**. Рекомендуемая среда для разработки и проверки процессов — Linux или Docker.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.runtime.txt
python scripts/make_demo.py demo_tasks/classification
python solution.py demo_tasks/classification/task.md --llm-mode mock
```

На Windows активируйте `.venv\Scripts\Activate.ps1` в PowerShell либо запускайте `.venv\Scripts\python.exe`. Полную проверку Linux-групп процессов выполняйте в Docker/WSL2.

Демонстрация регрессии:

```bash
python scripts/make_demo.py demo_tasks/regression --kind regression
python solution.py demo_tasks/regression/task.md --llm-mode mock
```

Mock — явно выбранный адаптер **только для синтетических задач** генератора. При ошибке live API переключения в mock нет. Обучение, метрики, процессы и выходной CSV в mock-режиме настоящие; имитируются ответы LLM.

## Предоставленный API

Скопируйте `.env.example` в `.env` и заполните значения из инструкций организаторов:

- `OPENAI_API_KEY` — обязательный ключ команды.
- `OPENAI_BASE_URL` — обязательный адрес предоставленного прокси.
- `OPENAI_MODEL` — необязательная модель; по умолчанию `qwen/qwen3.8-27b`. Прокси подставляет модель задачи.

```bash
python solution.py /absolute/path/to/task.md --env-file .env
```

Без `--env-file` читаются только переменные процесса. `.env` автоматически не загружается. Существующее окружение имеет приоритет; поддерживаются строки `KEY=value` и кавычки, без shell-подстановок. Адрес и ключ всегда берутся из env. Все live-запросы идут через один Gateway к указанному сервису; автоматического переключения на другой адрес нет.

Для локального запуска инструкция указывает `https://changellenge.up.railway.app/v1`, запасной адрес — `https://api.alfahack-gateway26.ru/v1`. Если нужен запасной, команда явно меняет `OPENAI_BASE_URL`. На платформе обе обязательные переменные подставляются ею; локальный `.env` загружать в ZIP не нужно.

Лимит ключа по инструкции — **600 рублей в день на всю команду**, сброс в **03:00 МСК**. При `Budget has been exceeded` Gateway останавливает новые обращения; после публикации первого ответа поиск может продолжаться локальными испытаниями каталога. Ошибка API сохраняется в журнале и статусе degraded. До получения первого проверенного ответа ошибка завершает запуск с ненулевым кодом. Каркас не вычисляет потраченные рубли по числу токенов и не ожидает сброса несколько часов.

```bash
python scripts/doctor.py
```

Диагностика показывает наличие API-переменных и совпадение версий библиотек, не раскрывая значения ключей.

## Откуда берётся задача

Один запуск обрабатывает **один `task.md`**. Платформа кладёт условие и данные в рабочую папку и запускает `python3 solution.py task.md`. Агент читает этот Markdown и связанные с ним файлы. Самостоятельного опроса очереди задач нет.

Локально сохраните исходную структуру распакованного архива и передайте путь к нужному условию. Не собирайте условия и CSV разных задач в одну папку:

```bash
python3 scripts/list_tasks.py data_for_participants
python3 solution.py "data_for_participants/Регрессия/task.md" --env-file .env
python3 solution.py "data_for_participants/Многоклассовая классификация/task.md" --env-file .env
```

Это два отдельных запуска. Приведённые имена каталогов взяты из структуры архива; таблицы для подготовки каркаса не анализировались. `list_tasks.py` проверяет только расположение файлов, не читает CSV и не вызывает модель.

Если вы специально скопировали **одну** задачу в корень проекта, рядом с её `task.md` должны находиться её `train.csv` и `test.csv`, а при наличии — её `sample_submission.csv` и `data_dictionary.csv`. После этого `python3 solution.py task.md --env-file .env` корректен. Итоговый `submission.csv` сохраняется по условию, обычно в этой же папке.

Файлы рядом с условием имеют приоритет перед одноимёнными файлами в подпапках. Необязательный шаблон ответа и словарь выбираются из папки выбранных данных/условия; шаблоны других задач не подхватываются рекурсивно. Если обязательные данные всё ещё неоднозначны, ошибка перечисляет кандидатов и предлагает выбрать конкретный `task.md`.

## Логи и результат

Итоговый путь берётся из текущей задачи, обычно `submission.csv` рядом с `task.md`. В `runs/<run_id>/` находятся:

| Путь | Что смотреть |
|---|---|
| `events.jsonl` | Сквозная хронология, trace/span/parent IDs, Cxx, ошибки, время |
| `messages/` | Полные JSON-запросы и ответы между модулями |
| `llm/` | Доступные запросы/ответы API и проверенные структурированные результаты |
| `contexts/` | Контексты исследователей и сводки экспериментов |
| `task/` | Исходное условие, TaskSpec, полный профиль, TOOL-каталог |
| `code/` | Python, реально переданный исполнителю |
| `experiments/` | JobSpec, stdout/stderr, результат процесса, snapshot модели |
| `submissions/` | Кандидаты CSV, проверки и состояния финализации |
| `state.sqlite` | Эксперименты, родители, оценки, события и журнал публикации |
| `summary.md` | Читаемый отчёт по запуску |
| `objects/<sha256>/content` | Неизменяемые manifests, checkpoints, capsules, trials и exports |
| `exports/final-*/` | Полный graph.json, ranking.json и типизированные graph-events.jsonl |
| `graph/owned-runtime.zip` | Зафиксированный собственный код для восстановления кандидата |

```bash
python scripts/show_run.py runs/ИМЯ_ЗАПУСКА --follow
python scripts/show_run.py runs/ИМЯ_ЗАПУСКА --contract C10
python scripts/show_run.py runs/ИМЯ_ЗАПУСКА --experiment exp-ID
```

«Размышления» фиксируются как доступные ответы модели, гипотеза, краткое обоснование и ожидаемый эффект; дополнительные скрытые рассуждения провайдера не предполагаются. Ключ API маскируется, в процессы обучения ключи не передаются. Каталоги запусков имеют отдельные run_id и не переносятся между задачами.

## Настройки

Официальные переменные отделены от внутренних в `.env.example`. Основные внутренние значения:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `TIME_BUDGET_SECONDS` | 10800 | Полное время, включая импорты, API и вывод; больше 3 часов запрещено |
| `MAX_WORKERS` | 2 | Независимые исследовательские контексты и максимум обучений |
| `TRAIN_CPU_THREADS` | 3 | До 3 потоков на обучение; до 6 суммарно |
| `TRAIN_MEMORY_MB` | 10240 | Лимит RSS на задание; два обучения до 20 GiB |
| `EXPERIMENT_TIMEOUT_SECONDS` | 600 | Запрошенный таймаут одного train-job |
| `RESEARCH_SERIES_SIZE` | 4 | Число связанных испытаний; от 1 до 16, включая исходный вариант |
| `CATALOG_WARMUP_EXPERIMENTS` | 4 | До четырёх проверенных конфигураций перед LLM-поиском |
| `RESEARCH_MODE` | catalog | Компактный выбор рецепта; code явно включает генерацию Python |
| `LLM_MAX_CALLS` | 32 | Общий предел API-попыток, включая retry и tool calls |
| `LLM_TIMEOUT_SECONDS` | 600 | HTTP timeout одной API-попытки |
| `LLM_OPERATION_TIMEOUT_SECONDS` | 1200 | Бюджет всего диалога, ожидания, повторов и tool calls |
| `LLM_MAX_OUTPUT_TOKENS` | 16384 | Стартовый бюджет исследовательского ответа |
| `LLM_BOOTSTRAP_OUTPUT_TOKENS` | 4096 | Старт для понимания задачи и выбора валидации |
| `LLM_MAX_OUTPUT_TOKENS_LIMIT` | 32768 | Верхняя клиентская граница повышения при обрыве |
| `LLM_MAX_TOTAL_OUTPUT_TOKENS` | 262144 | Резервируемая квота выходных токенов на запуск |
| `LLM_PROGRESS_SECONDS` | 15 | Интервал сообщений ожидания API |
| `CONSOLE_LOG_FORMAT` | human | Подробный терминал; json выводит полные JSONL-события |
| `MAX_CONTEXT_TOKENS` | 16000 | Консервативный byte-based предел контекста, не точный tokenizer |
| `LOG_MODEL_IO` | 1 | Сохранение raw API snapshots; структурированные планы и события сохраняются всегда |
| `GRAPH_REFINEMENT_ENABLED` | 1 | Завершать поиск доводкой измеренного лучшего решения |
| `GRAPH_SEARCH_FRACTION` | 0.85 | Доля исследования до доводки; допустимо 0.80–0.90 |
| `GRAPH_PLATEAU_SECONDS` | 900 | Минимальное время без существенного прогресса перед плато; нужны также четыре разные попытки от каждого peer |

`MAX_RESEARCH_EXPERIMENTS` читается для совместимости со старыми настройками и не останавливает поиск. Квоты `LLM_MAX_CALLS` и `LLM_MAX_TOTAL_OUTPUT_TOKENS` ограничивают только обращения к модели. Новое обучение допускается, если прогноз его длительности и запас на итоговое обучение и сохранение результата укладываются в оставшееся время. Проверенный ранний CSV сохраняется до готовности лучшего ответа. Повторы и неудачные предложения заменяются другими допустимыми конфигурациями.

## Поддерживаемая граница v0.3

- Табличные CSV UTF-8, запятая, одна целевая переменная и одна колонка предсказания.
- Регрессия, бинарная и многоклассовая классификация.
- RMSE, MAE, R², Macro F1, Weighted F1, Accuracy.
- Случайный, стратифицированный, групповой и временной holdout. Временная колонка — числовой порядок либо ISO-8601.
- Dummy, линейный рецепт, HistGradientBoosting, RandomForest, ExtraTrees; CatBoost включается при наличии разрешённой зависимости. Для регрессии доступны identity и shifted_log1p цели, обучаемые только на fit-строках.
- Python `make_pipeline(task_spec, params)`, предобработка внутри pipeline, общий runner и оценщик.

Неизвестный тип/метрика/формат возвращает явную ошибку. Приватные задачи заранее неизвестны; дополнительные адаптеры и метрики нужно расширять в реестрах, сохраняя общий протокол. Пример не обещает соревновательное качество без дальнейшего исследования.

## Проверка и упаковка

```bash
python scripts/check.py
python scripts/package_solution.py
```

Полный набор можно выполнять в трёх независимых процессах: `python scripts/check.py --jobs 3`.
Проверки используют отдельные временные каталоги; обычный запуск остаётся последовательным.

Второй скрипт создаёт **плоский** `dist/solution.zip`: `solution.py`, точный официальный `requirements.txt` и отдельные читаемые `.py`-модули в корне, без каталогов. Каждый исходник агента сохраняется побайтово: например, `agent/graph/controller.py` лежит как `agent_graph_controller.py`, а `agent/llm/gateway.py` — как `agent_llm_gateway.py`. Повторная сборка тех же исходников даёт те же байты.

Модульная структура сохраняется в Git. Платформенный `solution.py` содержит понятный список файлов и копирует соседние исходники в обычные package-каталоги под `/tmp`, затем вызывает наш `agent.runtime.main`. В нём нет base85, сжатого Python-кода или встроенного архива. SQL, JSON и Markdown записаны открытыми строками в `stepan_resources.py`: платформа копирует только `.py` и `requirements.txt`. Обучающие subprocess используют тот же временный код; каталог удаляется после завершения. Копирование и импорты входят в общий бюджет времени.

Сторонние библиотеки, данные, ключи, логи, модели, тесты и документация в платформенный ZIP не входят. Зависимости ставит платформа по `requirements.txt`. `requirements.runtime.txt` — только разрешённое подмножество для локальной разработки и Dockerfile. Его нельзя подставлять вместо официального `requirements.txt` в платформенный ZIP. Подробности: `docs/PLATFORM.md`.

Для локальной проверки контейнера:

```bash
docker build -t alfa-automl-agent .
docker run --rm --cpus=8 --memory=32g --env-file .env -e WORK_DIR=/runs -v "$PWD/demo_tasks/classification:/task" -v "$PWD/runs:/runs" alfa-automl-agent /task/task.md
```

Для mock-десктопного прогона добавьте к Docker-команде после пути задачи `--llm-mode mock`. Dockerfile — локальный образ; официальную среду запуска предоставляет платформа. Установка пакетов выполняется при подготовке среды, не во время решения задачи.

Фактически выполненные проверки и версии среды зафиксированы в `docs/VALIDATION.md` и `docs/VALIDATION-GRAPH.md`; читаемая поставка v0.4.1 проверяется отдельно в `docs/VALIDATION-PACKAGING.md`. Live API и CatBoost требуют проверки в среде с установленными pinned-зависимостями и доступом организаторов.

Если API отвечает `503 ... OpenrouterException - Insufficient credits`, это отказ доступа у внешнего
провайдера до обучения модели. Gateway возвращает `LLM_PROVIDER_CREDITS_EXHAUSTED`, прекращает retry
и новые API-вызовы в текущем запуске. Эта ошибка не устанавливает остаток командных 600 RUB или время
сброса: их по такому ответу определить нельзя. Для восстановления доступа нужен оператор шлюза.

## Обновление с v0.2: один локальный шаг

Старый `.env` имеет приоритет над новыми defaults, поэтому одного git pull недостаточно.
Примените новые не секретные настройки, сохранив ключ, URL, модель, LLM_MODE и пути:

```bash
python scripts/configure.py
python scripts/configure.py --apply
```

Первый вызов показывает предлагаемые значения; второй атомарно обновляет существующий `.env`.
Секреты не печатаются. Значения, уже экспортированные в окружение процесса, по-прежнему приоритетнее файла.

## Как теперь идёт поиск

v0.3.1 исправляет ложную отмену успешного train/refit: завершившийся worker может оставить
служебные процессы библиотеки. Runner останавливает их перед освобождением ресурсов и определяет
результат по exit code и `result.json`. Очистка группы сама по себе больше не превращает успех
в `JOB_CANCELLED`. Настройки `.env` после v0.3 менять не требуется; нужен новый запуск задачи.

После раннего CSV агент измеряет до четырёх проверенных конфигураций без дополнительных LLM-запросов.
На регрессии это, при наличии библиотек, CatBoost/HGB с identity и shifted_log1p; без CatBoost список
дополняют другие доступные семейства. В graph mode каждый peer получает собственную базу;
каждый peer получает три exploit на один explore. В контексте есть фактические параметры, преобразования,
метрики и отметка incumbent. Планы проходят прежние дедупликацию, общий split, evaluator и Publisher.

В `RESEARCH_MODE=catalog` модель возвращает ResearchChoice-v1: рецепт, параметры, гипотезу и ожидаемый
эффект. Проверенный Python формирует estimator и кодовый артефакт через C11. Сгенерированных
конструкторов и повторной отправки кода через tool call нет. `RESEARCH_MODE=code` сохраняет прежний
режим экспериментов с собственным Python; его риски и ограничения AST остаются прежними.

Терминал показывает call/attempt, model, output cap, usage/finish_reason, heartbeat ожидания,
гипотезу, параметры, этап fit/predict, RAM/таймауты, ошибку worker с путём к stderr,
валидационные метрики и изменение к baseline. `run.finished state=degraded` выделяется WARNING.
Полные доступные API-сообщения остаются в `runs/`; скрытые рассуждения не восстанавливаются.

Аудит токенов без чтения CSV/моделей и без обращений к API:

```bash
python scripts/analyze_run.py runs/ИМЯ_ЗАПУСКА
python scripts/analyze_run.py /path/to/run.zip --json
```

Основание стартовых лимитов, резервирование и ограничения денежных оценок — `docs/TOKEN_BUDGET.md`.
Более широкий поиск не обещает конкретный RMSE: следующая проверка качества выполняется на том же
протоколе, затем на других публичных задачах и платформе. Тесты проверяют работу механизма;
соревновательное качество подтверждается отдельными экспериментами.
