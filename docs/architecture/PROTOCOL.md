# Архитектура AutoML-агента · v0.1.0

Предлагаемый контракт для согласования командой из трёх человек. Дата: 21 октября 2026 года. Это проект интерфейсов, а не реализованный агент. Все JSON-примеры, имена полей демонстрационного датасета, размеры и метрики синтетические. При подготовке этого пакета CSV из материалов хакатона не анализировались.

## Как читать пакет

- `automl-architecture.html` — интерактивная карта: выберите фазу и переход C00–C24; ниже находятся запрос, ответ, схема и инварианты.
- `architecture.svg` — большая векторная схема всех фаз для обсуждения и печати.
- `contracts.json` — единый реестр операций, примеров и владельцев.
- `contracts.schema.json` — JSON Schema Draft 2020-12, по одной паре схем на операцию.
- `examples/Cxx/` — успешный запрос, успешный ответ и ответ с ошибкой.
- `contracts.md` — все контракты с полными JSON-телами.
- `PROTOCOL.md` — общие правила, состояния, интеграция и распределение работы.

## Принятое устройство

Один процесс управления Python владеет состоянием запуска, SQLite и общим бюджетом. LLM интерпретирует задачу, формулирует гипотезы и готовит ограниченные изменения кода. Два независимых исследовательских контекста работают через общую очередь. Обучение идёт в отдельных процессах под контролем runner. Оценщик самостоятельно считает метрики. Только Publisher заменяет итоговый файл.

`POST /v1/...` — имена логических внутренних операций. В MVP не нужны HTTP-сервер, FastAPI, брокер сообщений или контейнер на каждый блок. Контракт реализуется Python-вызовом с сериализуемыми объектами; асинхронные события передаются локальной очередью. REST-подобная запись фиксирует границу ответственности и позволит при необходимости добавить HTTP-адаптер позже.

Внешняя граница платформы: запуск `python solution.py /path/to/task.md`, переменные из baseline и выходной файл в формате текущей задачи. Обёртки JSON ниже создаёт наше приложение. Платформа не вызывает C00–C24.

## Что взято из материалов, а что предлагается

| Зафиксировано материалами | Предлагается нами |
|---|---|

## Единая обёртка

Запрос:

```json
{
  "schema_version": "1.0",
  "request_id": "req-unique-attempt",
  "run_id": "run-demo-001",
  "idempotency_key": "stable-logical-operation-key",
  "payload": {}
}
```

Ответ:

```json
{
  "schema_version": "1.0",
  "request_id": "req-unique-attempt",
  "run_id": "run-demo-001",
  "ok": true,
  "data": {},
  "error": null
}
```

При ошибке: `ok=false`, `data=null`, `error={code,message,retryable,retry_after_seconds,details}`. JSON не содержит NaN, Infinity, Python-объектов, массивов всех строк датасета, моделей или секретов. Большие результаты передаются через идентификаторы артефактов.

- `request_id` — идентичность конкретного запроса; повторная попытка получает новый request_id, сохраняя idempotency_key. Воспроизведённый ответ возвращает request_id текущей попытки.
- `run_id` обязателен везде, включая события и ссылки на артефакты. Между разными задачами состояние не переносится.
- `idempotency_key=null` допустим для чтения. Для записи ключ обязателен по семантическим правилам операции. Повтор с тем же ключом и другим payload возвращает `IDEMPOTENCY_CONFLICT`.
- Успешный ответ `accepted` означает только принятие фоновой работы. Готовность приходит отдельным C15.
- Верхние поля и поля закрытых объектов схемы запрещают неизвестные ключи. `hyperparameters`, `feature_steps`, параметры метрик и стратегий имеют расширяемую структуру; их дополнительно проверяет выбранный recipe/adapter/metric registry.
- Версия схемы и версия пакета различаются: `schema_version=1.0` — версия обёртки, `v0.1.0` — предлагаемый набор доменных контрактов. Пока команда не согласовала v0.1, изменения допустимы; затем несовместимые изменения версионируются.

## Общие типы

| Тип | Ключевые правила |
|---|---|
| TaskSpec | Таргет, тип задачи, метрика с направлением, допустимые значения, входные артефакты и точный OutputSpec |
| ExperimentPlan | Гипотеза, родители, recipe, параметры, шаги признаков, код, seed, fidelity, validation_id, ресурсы |
| ArtifactRef | run_id, относительный путь внутри workspace, media type, размер и SHA256 фактических байтов |
| MetricValue | value и полный ключ сравнимости: датасет, протокол, метрика, направление, fidelity |
| Lease | Ограничения обучения, timeout, heartbeat и fencing token конкретной попытки |
| Evaluation | Только результат доверенного оценщика; failed/invalid не получает выдуманный numeric score |
| Champion | Проверенный эксперимент, готовый выходной артефакт, hash и монотонная версия публикации |

Все поля в показанных схемах обязательны; nullable-поля передаются явно как null. Конкретные типы, enum, вложенность и запрет лишних полей находятся в `contracts.schema.json`. Семантические ограничения, связывающие несколько полей и сохранённое состояние, проверяются приложением дополнительно.

### Расширяемость задачи

Первый MVP: regression, binary_classification, multiclass_classification. Это граница первоначальной реализации, а не утверждение о приватном наборе. Метрика выбирается по условию через registry. Неизвестный тип задачи или метрика не подменяются привычной задачей: возвращается `UNSUPPORTED_TASK_KIND` / `UNSUPPORTED_METRIC`.

В `contracts.json/task_examples` есть отдельные примеры классификации и регрессии. В ветке регрессии меняются adapter, metric, допустимые предсказания и рецепты; диспетчер, очередь, дедупликация и сохранение ответа остаются общими.

## Последовательность запуска

1. C00 создаёт runtime и фиксирует монотонный deadline.
2. C01 читает условие. C02 извлекает семантику через C10, C03 собирает технический профиль. Независимые операции можно выполнять конкурентно под общим бюджетом.
3. C04 проверяет TaskSpec обычным кодом. C05 фиксирует валидацию; C06 выбирает доступные рецепты и инструменты.
4. Сначала выполняется быстрый baseline: C07 → C08 → C09 → C10/C11 → C12 → C13 → C14 → C15 → C16 → C17. Baseline имеет ту же запись эксперимента и тот же протокол, что последующие кандидаты.
5. Для первого валидного baseline сразу выполняется C18 → C13 → C19 → C15 → C20 → C21. Только после появления готового ответа начинается основной поиск.
6. C07–C17 повторяются для двух исследовательских контекстов. Одинаковый план резервируется только один раз. Новое улучшение инициирует подготовку ответа; старый CSV остаётся на месте.
7. C22 закрывает поиск по бюджету; завершается допустимая финализация. C23 проверяет опубликованный ответ и завершает процесс. Вызова платформенного submit API нет.

## Состояния и владение

| Объект | Состояния | Кто меняет |
|---|---|---|
| Run | initializing → baseline → searching → finalizing → completed / degraded / failed | Runtime / Orchestrator |
| Experiment | queued → running → trained → evaluated; альтернативы: invalid, failed, timed_out, cancelled | Orchestrator через store |
| Job | accepted → running → succeeded / failed / timed_out / cancelled | Runner, подтверждает обработчик C15 |
| SubmissionJob | preparing → refitting → validating → published; альтернативы: failed, timed_out, cancelled, skipped_not_better | Finalizer / Publisher |
| Lease | acquired → renewed → released; при потере heartbeat — expiring → process_stopped → released | BudgetManager |

`best_evaluated` — указатель на лучший проверенный эксперимент. `published_champion` — указатель на лучший уже готовый и сохранённый ответ. Они не являются состояниями Experiment и могут указывать на разные записи.

Метрика сравнивается только при совпадении dataset_id, validation_id, metric_id, direction, fidelity и реализации оценщика, включённой в hash протокола. Кандидат с screening-fidelity сначала проходит full-проверку. При изменении схемы валидации создаётся новая версия и пересчитываются сопоставляемые кандидаты.

## Два исследователя и повторные события

Researcher-1 получает поручение улучшать текущего кандидата, Researcher-2 — проверять альтернативное направление. Это стартовая стратегия, которую можно менять. Два независимых контекста не требуют двух параллельных обучений при нехватке RAM.

Fingerprint строится диспетчером по нормализованной фактической конфигурации с раскрытыми defaults. Включаются версии данных, задачи, протокола, рецепта и кода, model params, feature steps, seed и fidelity. Не включаются человекочитаемая гипотеза, researcher_id и путь workspace.

`UNIQUE(run_id,fingerprint)` резервирует логическую запись. Попытки исполнения имеют отдельные attempt_no и fencing token. Потеря heartbeat не означает, что старое обучение уже остановилось: перед повтором и выдачей ресурсов runner останавливает и подтверждает завершение дерева процессов. Это исключает запуск дубля при работающем осиротевшем процессе. Поздние сообщения старой попытки отклоняются.

События C15 доставляются at-least-once и фиксируются один раз по `UNIQUE(run_id,event_id)`. Для выполнения arbitrary Python не заявляется гарантия exactly-once. Все выходные файлы имеют уникальные пути для попытки.

## Сохранение ответа без ухудшения

1. Finalizer обучает проверенный pipeline на полном train и предсказывает test в отдельный кандидат.
2. OutputValidator проверяет точную схему, значения, идентификаторы и порядок.
3. Publisher под единственным lock повторно читает текущего чемпиона и сравнивает проверенные оценки.
4. Готовит temp-файл в каталоге выходного submission.csv, проверяет hash, выполняет flush/fsync.
5. Записывает durable publication journal, атомарно заменяет файл через os.replace и фиксирует champion metadata. Для устойчивости к сбою питания после replace выполняется fsync каталога, где это поддерживается.
6. При рестарте сверяет journal и фактический hash файла. Атомарности между SQLite и filesystem не предполагается.

При конфликте версии кандидат сравнивается заново. Запоздалый худший кандидат получает skipped_not_better. Если новый кандидат не успел refit или сломал формат, уже готовый ответ остаётся доступен. Принудительную остановку на 3 часах нельзя использовать как сигнал начать запись: к этому моменту запись должна быть завершена.

## Ресурсы, LLM и инструменты

- Начальные внутренние лимиты: MAX_WORKERS=2, TRAIN_CPU_THREADS=3, TRAIN_MEMORY_MB=10240. Итоговый суммарный предел учитывает родительский процесс и дочерние процессы, а не только один PID. Ограничение памяти нужно реализовать средствами среды или watchdog с запасом; один объект Lease сам лимит не обеспечивает.
- Deadline охватывает чтение файлов, импорты, LLM, обучение, refit и вывод. Запас на финализацию оценивается по наблюдаемым длительностям плюс запас. Значения 600/900/1200 секунд в JSON — демонстрационные внутренние настройки.
- LLMGateway объединяет учёт запросов, ограничение конкуренции, retry и фактические usage-поля, если провайдер их отдаёт. Дневной денежный лимит из ТЗ относится к разработке; точный платформенный бюджет запросов отдельно не предполагается.
- Контекст содержит постоянный префикс, TaskSpec и ограниченную сводку. Полные логи остаются артефактами. Поддержка серверного prefix cache не требуется для работоспособности.
- Tools.md и схемы tools генерируются из единого каталога. Механизм tool calls не требует MCP; при выборе MCP его наличие в проверочной среде нужно проверить.
- Runner управляет загрузкой данных, fit/predict и ограничениями. Сгенерированный код экспортирует make_pipeline(task_spec, params). Контракт fit/predict, допустимые fit kwargs и правила обработки категорий задаёт рецепт; preprocessing fit выполняется только на обучающей части.
- Изоляция каталогов и скрытые от обычного контекста labels защищают от случайных ошибок, но сами по себе не являются OS-песочницей для произвольного Python. При расширении генерации кода права и изоляция проектируются отдельно.

## Артефакты и память

Предлагаемые таблицы SQLite: runs, task_specs, validation_protocols, experiments, experiment_parents, attempts, job_events, evaluations, leases, submission_jobs, publication_journal, publications, artifacts, idempotency_records. В MVP это один sqlite-файл, migrations в Git и единственный писатель — диспетчер.

Файлы: task/profile/context summaries; code; model/pipeline; validation predictions; diagnostics; logs; staged submissions. В SQLite хранятся metadata, hash и ссылки. DataFrame и model bytes через LLM/JSON не передаются. Parent links образуют DAG, отдельная graph DB и vector DB не нужны для первого цикла.

Входные данные логически read-only. Итоговый путь пишет только Publisher. API-ключи не передаются дочерним training-процессам; окружение для них содержит необходимые системные значения, кодировку и согласованные thread limits. Ключи и .env исключаются из Git.

## Распределение команды

| Владелец | Область | Модули | Первый проверяемый результат |
|---|---|---|---|
| A | Исполнение и интеграция | solution, config, orchestrator, runner, store, budget | Два синтетических задания, дедупликация, таймаут и повтор события не ломают состояние |
| B | LLM, контекст и гипотезы | llm, prompts, task_reader, task_interpreter, context, catalog | Из текста получается draft, из контекста — валидный план, инструменты вызываются по схемам |
| C | ML и ответ | task_spec, profile/code tools, recipes, evaluation, submission | Один рецепт проходит split-оценку, full refit и проверку выходного CSV |

Владелец контракта отвечает за реализацию принимающей стороны и её фиксацию в спецификации, даже если вызывающий код пишет другой участник. Схемы и fixtures — общий небольшой PR; после его принятия стороны разрабатываются независимо. Для C19 контракт runner реализует A, а orchestration refit и приёмку согласует C.

### Очерёдность интеграции

1. Вместе согласовать envelope, TaskSpec, ExperimentPlan, ArtifactRef и правила сравнения.
2. На fixtures C00/C04/C05/C12/C14/C15/C16/C17/C18/C19/C20/C21 получить один полный проход без LLM. Fixture-адаптер допустим только в локальном тестовом режиме, а не как скрытая подмена агента при сдаче.
3. B подключает реальный LLMGateway и генерацию проверяемого плана/кода. Остальные контракты сохраняются.
4. Подключить второго исследователя и проверить конкурентный одинаковый план, позднее событие и refit, завершающийся после более нового кандидата.
5. Проверить короткий искусственный deadline, сбой LLM, невалидные predictions и остановку обучения: прежний готовый CSV остаётся доступен.
6. Прогнать ZIP в среде Python 3.12 с зависимостями организаторов. Пакет этого документа не является ZIP решения для платформы.

## Что нужно уточнить у организаторов перед окончательной упаковкой

- Наличие `mcp`: baseline импортирует его, requirements не содержит отдельной строки; это не доказывает отсутствие транзитивной установки.
- Реальная раскладка путей в контейнере: относительные пути из task.md и структура скачанного архива расходятся. Resolver не должен угадывать при нескольких совпадениях.
- Доступность API, rate limits и возможный отдельный бюджет запросов в проверочном запуске. Серверное кэширование контекста в материалах не обещано.

Эти уточнения не блокируют разработку внутренних контрактов.

## Внешняя граница LLM: нативное тело из адаптера C10

Пример построен по использованию `client.chat.completions.create` в предоставленном baseline. Поле `$OPENAI_MODEL` в примере — обозначение подстановки реального значения переменной окружения, а не строка, которую нужно отправлять буквально. OPENAI_BASE_URL и OPENAI_API_KEY передаются клиенту через env. Значение ключа не включается в messages, внутренние JSON или логи.

Здесь нет нашей обёртки schema_version/run_id: это формат внешнего API. В gateway сохраняется связь completion_id ↔ request_id ↔ run_id. Специальные режимы structured outputs, серверное prefix caching и возможность одновременных tool calls не предполагаются. Лимиты output и дополнительные параметры перед использованием проверяются на предоставленном endpoint.

Запрос:

```json
{
  "model": "$OPENAI_MODEL",
  "messages": [
    {
      "role": "system",
      "content": "Ты DS-агент. Работай через объявленные инструменты; итоговые гипотезы возвращай по согласованной схеме."
    },
    {
      "role": "user",
      "content": "Синтетический контекст задачи и проверенная сводка экспериментов."
    }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "write_code",
        "description": "Записать Python-код эксперимента в отдельный артефакт.",
        "parameters": {
          "type": "object",
          "properties": {
            "researcher_id": {
              "type": "string",
              "minLength": 1
            },
            "filename": {
              "type": "string",
              "minLength": 1
            },
            "content": {
              "type": "string",
              "minLength": 1
            },
            "declared_entrypoint": {
              "enum": [
                "make_pipeline"
              ]
            }
          },
          "required": [
            "researcher_id",
            "filename",
            "content",
            "declared_entrypoint"
          ],
          "additionalProperties": false
        }
      }
    }
  ],
  "parallel_tool_calls": false
}
```

Ответ с запросом инструмента:

```json
{
  "id": "completion-demo-001",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
```

`function.arguments` — JSON, сериализованный в строку. Gateway разбирает его, валидирует по схеме инструмента, добавляет внутренний envelope и выполняет C11. Результат возвращается модели сообщением role=tool:

```json

  "role": "tool",
  "tool_call_id": "call-001",
  "content": "{\"schema_version\": \"1.0\", \"request_id\": \"req-c11\", \"run_id\": \"run-demo-001\", \"ok\": true, \"data\": {\"artifact\": {\"artifact_id\": \"art-code-001\", \"run_id\": \"run-demo-001\", \"kind\": \"python_source\", \"relative_path\": \"experiments/plan-001/experiment.py\", \"sha256\": \"fe1b98a2038e60db754a844569a56ffeade70fed57fc70881fc2839f330413b7\", \"size_bytes\": 153, \"media_type\": \"text/x-python\"}, \"syntax_valid\": true, \"entrypoint\": \"make_pipeline\"}, \"error\": null}"
```

После исполнения инструмента диалог продолжается до структурированного конечного результата либо общего лимита. На каждом шаге проверяется дедлайн. tool_calls из ответа провайдера не дают разрешения менять итоговый submission.csv или читать файлы вне согласованной области.

## Подтверждённая остановка

C22 сообщает диспетчеру о необходимости завершить поиск или отменить задания. Для каждого активного задания диспетчер вызывает C24. Только process_tree_stopped=true разрешает C13 release. C15 фиксирует терминальное событие идемпотентно. C23 выполняется после остановки фоновых jobs и завершения публикации.
