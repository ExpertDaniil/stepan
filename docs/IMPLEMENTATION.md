# Реализация и соответствие ТЗ

Это каркас v0.2.0, построенный по согласованной схеме и уточнённой инструкции по ключам/загрузке. Контракты JSON находятся в `contracts/`, исходная схема — в `docs/architecture/`. Их REST-подобные имена реализованы локальными вызовами Python. Актуальные правила поставки: `PLATFORM.md`; исходная схема отражает предыдущую версию требований.

## Последовательность

C01 читает Markdown и разрешает пути. C03 собирает профиль, чтобы C02 видел реальную техническую схему. C04 проверяет извлечённые значения обычным кодом. LLM отдельно предлагает протокол C05 из четырёх поддерживаемых holdout-стратегий. Каталог C06 публикует инструменты и рецепты.

Ранний Dummy проходит ту же проверку метрики, full refit и проверку формата, что дальнейшие модели. После его публикации два LLM-контекста конкурентно предлагают по одному плану. Dispatcher резервирует планы транзакционно, запускает максимум два процесса и обрабатывает их события. В конце пачки готовится только лучший кандидат. Это сохраняет два исследовательских потока и ограничивает расходы на лишние refit.

Состояния train: queued → running → trained → evaluated; ошибки: failed/timed_out/cancelled/invalid. `best_evaluated` и `published_champion` хранятся отдельно. Финализация проходит preparing → refitting → validating → published либо явную ошибку. Её снимки находятся в `submissions/`.

## Что обеспечивает каркас

- Python 3.12; ZIP запускается с переданным путём к task.md, default — task.md.
- В платформенном ZIP только корневые `solution.py` и `requirements.txt`. Собственный runtime встроен в Python и разворачивается в `/tmp`; загрузчик платформы не должен сохранять подпапки исходников. Версии/полный список `requirements.txt` совпадают с исходным списком организаторов. Локальное подмножество — `requirements.runtime.txt`.
- Native API-клиент берёт ключ/адрес только из OPENAI_API_KEY/BASE_URL. OPENAI_MODEL необязателен; документированный default — qwen/qwen3.8-27b, прокси подставляет модель задачи. Fallback на другой сервис отсутствует.
- Дневной бюджет 600 RUB общий для ключа команды. Маркер `Budget has been exceeded` блокирует повторные и последующие запросы в текущем Gateway, не ожидая сброса в 03:00 МСК. Уже опубликованный проверенный результат сохраняется.
- Каждый запуск изолирован новым run_id. Перенос обученных моделей и опыта между задачами отсутствует.
- Сравниваются локальные метрики по общему dataset/protocol/fidelity. Платформа не даёт промежуточную оценку и не вызывается из исследовательского цикла.
- Дедлайн учитывает импорты, подготовку, API, train, refit и запись. Worker имеет собственные watchdog wall-time/peak-RSS, parent — наблюдение за группой и heartbeat. Более 10800 секунд в Config задать нельзя.
- Новое обучение резервирует до 3 CPU и 10 GiB. Потоки BLAS/OpenMP и n_jobs ограничены. Два задания используют до 6 CPU / 20 GiB, оставляя запас общей среде 8 CPU / 32 GB.
- RAM watchdog — периодическая проверка RSS, не отдельный kernel-cgroup на каждый job. Общий жёсткий предел обеспечивает платформа или `docker run --memory/--cpus`.
- Runner создаёт отдельную группу процессов. C24 подтверждает остановку до освобождения ресурсов. Ключи API не входят в окружение обучения.
- CSV проверяется по числу строк, точным колонкам, текстовому порядку id, допустимым классам и конечности чисел. Ведущие нули id сохраняются.
- Готовый CSV заменяется атомарно через temp того же каталога. Он доступен для чтения evaluator-процессу. SQLite/filesystem не объявляются общей транзакцией: publication journal закрывает окно сбоя после replace.

Один запуск принимает одно условие. Явные существующие пути из task.md имеют приоритет, затем для train/test выбираются файлы рядом с условием. Если их нет, поиск стандартного имени допускается только при единственном совпадении внутри task root, без `.venv`, `.git`, `runs/` и других служебных каталогов. Необязательный sample_submission/data_dictionary ищется только у выбранных данных либо рядом с условием. Неоднозначность и выход за task root возвращают ошибку. `scripts/list_tasks.py` перечисляет условия и проверяет только наличие/однозначность путей.

## Проверка кода и метрики

Generated code содержит `make_pipeline(task_spec, params)`. Runner передаёт `_cpu_threads` и `_seed`, ограничивает параметры потоков и владеет fit/predict. Условие, evaluator и итоговый файл исследователь не изменяет через объявленные инструменты. AST-проверка ограничивает импорты и очевидные опасные вызовы, но не является OS-песочницей произвольного Python. При дальнейшем расширении генерации изоляция проектируется отдельно.

Метрика рассчитывается по предсказаниям evaluator-кодом, а не принимается из текста LLM. Индексы split и реализация оценщика входят в hash протокола. Пропуски входных признаков — только пустые ячейки; строковая категория `NA` сохраняется.

Fingerprint содержит версию данных/задачи/валидации/рецепта, фактические параметры с defaults, hash кода, feature_steps, seed и fidelity. Отпечатки исключают researcher_id и словесную гипотезу. В v0.1 дедупликация точная; семантически эквивалентный Python с другим исходным текстом может получить другой hash.

## Уточнения исходной схемы

- Логический C21 idempotency key включает experiment_id и hash кандидата: два разных эксперимента могут дать одинаковый CSV при разных валидационных оценках.
- C19 соблюдает output_relative_path; все промежуточные пути остаются внутри run workspace.
- Полный C03-профиль и data_dictionary сохраняются артефактом; LLM получает ограниченную сводку. Усечения фиксируются явно.
- Вложенные вызовы получают parent_span_id. Полные модели и таблицы не проходят через JSON/LLM.
- Работа возобновляется новым run_id, без автоматического resume старого исследования. Publication journal поддерживает согласование записи в рамках того же run, если файл уже заменён.
- Ошибка live API после baseline завершает поиск с проверенным готовым ответом и state=degraded. Ошибка до проверенного ответа возвращает ненулевой exit code.
- Источники task/metric ограничены текущим ТЗ, схемой и входными файлами. Неподдерживаемый формат не подменяется знакомым.

## Следующие независимые задачи

A: очередь с более гибким backpressure, persisted retry attempts, дополнительные контроли процессов.
B: анализ ошибок по артефактам, улучшение diversity поручений, более точный подсчёт контекста при доступном tokenizer сервиса.
C: CV, OOF-ансамбли, дополнительные метрики/форматы ответа, новые проверяемые преобразования признаков.

MCP не используется и не требуется. Это снимает зависимость от неявной установки mcp в baseline. Несовпадение путей архива обрабатывает task-local resolver. Raw API и CatBoost нужно отдельно прогнать в среде организаторов; endpoint и rate limits не выдумываются.
